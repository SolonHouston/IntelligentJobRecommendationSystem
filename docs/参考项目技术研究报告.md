# 五个开源参考项目技术研究报告

> 研究对象：`zhipin-shield`、`job-crawler`、`ZhaopinData`、`JobCrawlerSystem`、`RoleFit`  
> 目标项目：《基于 Vue 和 SpringBoot 的智能职位推荐系统的设计与实现》  
> 研究方式：只读检查固定提交下的 README、目录结构和与毕设直接相关的核心源码；未安装依赖、未启动服务、未执行采集或测试。本文的“已实现”仅表示源码链路存在，不代表本轮已完成真实网站、模型 API 或生产环境验证。

## 1. 结论摘要

五个项目没有一个适合整套迁入。最佳组合是：

- 用 **zhipin-shield** 参考多来源适配、统一职位模型、合并去重和可解释规则评分。
- 用 **job-crawler** 参考采集规则、任务、日志、定时器、规范化与数据库更新的紧凑骨架。
- 用 **ZhaopinData** 补充智联详情页字段清单、逐条详情采集和中途落盘思想。
- 用 **JobCrawlerSystem** 参考“任务入队—工作进程—状态回写”的生命周期，以及 BOSS JSON 字段映射；不照搬 Django、Celery、Redis、Scrapy 和 Agent 全栈。
- 用 **RoleFit** 重点参考简历结构化、岗位画像、技能标准化、分维度匹配、推荐解释和技能差距。

建议先完成站内招聘业务与统一职位库，再接入可控的数据导入和确定性推荐，最后才考虑外部自动采集、向量检索和行为推荐。真实招聘网站的自动采集存在登录、验证码、反爬、服务条款和数据授权风险，不应成为毕设能否完成的前置条件。

## 3. zhipin-shield（职盾）

### 3.1 多来源职位接入与统一模型

1. **在我们的系统中有什么作用？** 让站内职位、文件导入和未来经授权的外部来源共用一条规范化链路，避免业务代码与某个招聘网站耦合。
2. **原项目通过什么代码实现？** `core/models.py:24-60` 定义 `JobPosting`，统一来源、标题、公司、城市、薪资、经验、学历、URL、描述和发布时间等字段；`collect/adapters/base.py:7-50` 定义 `BaseAdapter.search(SearchQuery)`；`core/aggregators.py:12-41` 逐个调用适配器、隔离单来源异常、合并去重并按薪资排序。`collect/adapters/real_skeleton.py:7-81` 主要把浏览器采集后的 JSON 转成统一对象，因此真实来源适配只是**部分实现**，不是成熟、独立的采集 SDK。聚合器注释提到并发，但当前循环实际是顺序执行。
3. **我们如何用 Java/Spring Boot 实现？** 定义 `JobSourceProvider`：`sourceCode()`、`fetch(JobFetchRequest)`；分别实现 `InternalJobProvider`、`FileImportJobProvider` 和经授权的外部来源 Provider。Provider 只产生 `ExternalJobRaw`，统一交给 `JobNormalizer`、`JobValidator`、`JobDeduplicator` 和 `JobUpsertService`，不允许各来源直接写核心 `job` 表。

### 3.2 清洗、合并与去重

1. **作用：** 把不同格式的职位归一，并在重复采集时保留有效详情、更新动态字段。
2. **原实现：** `collect/collect.py:155-196` 清理公司名、规范城市并按最低薪资和关键词过滤；`collect/collect.py:359-367` 用“规范公司名前 12 字符 + 标题前 16 字符”生成去重键；`collect/collect.py:655-703` 合并本次与历史 JSON，并保留已有详情文本。该链路已实现，但短字符串键容易误合并同名岗位，也可能漏掉换标题或跨城市的同一职位。
3. **Java 实现：** 优先用唯一键 `(source_code, source_job_id)`；缺少稳定来源 ID 时，再计算规范化 `company + title + city + salary_band + jd_hash` 指纹。保留 `job_source_record` 原始记录、抓取时间和内容哈希；核心 `job` 表通过事务性 upsert 更新 `last_seen_at`、状态和可变字段，并记录字段来源。

### 3.3 可解释职位匹配

1. **作用：** 在 LLM 不稳定或不可用时仍能给出可复现的推荐顺序、命中理由和技能差距。
2. **原实现：** `score/matcher.py:315-399` 计算技能命中/缺失、类别、经验和学历惩罚并生成理由；`score/matcher.py:451-491` 组合薪资、匹配、区域和雇主等维度并排序分档；`server.py:343-448` 串起聚合、过滤、评分和结果筛选。属于**已实现的规则评分链路**。
3. **Java 实现：** 建立 `MatchDimension` 与可配置权重，输出总分、各维度分、证据、`matchedSkills`、`missingSkills` 和理由模板。排序必须由确定性服务完成，LLM 只负责把已计算证据改写成自然语言，不直接决定排名。

### 3.4 评价

- 优点：抽象简单，统一模型和理由生成最适合毕设第一版。
- 不足：无 MySQL 持久化、任务状态和增量同步；异常处理较宽泛；真实来源依赖浏览器态。
- 许可：README 声称 MIT，但仓库未发现独立 `LICENSE` 文件，正式复用代码前须向上游确认许可；当前更适合借鉴思想后自主实现。

## 4. job-crawler

### 4.1 采集任务、规则、日志与定时执行

1. **在我们的系统中有什么作用？** 让管理员可创建规则、查看进度与错误、停止任务、定时更新来源职位。
2. **原项目通过什么代码实现？** `backend/app/crawler/engine.py:22-143` 遍历“关键词 × 城市”，选择站点适配器，抓取、规范化、更新数据库并收集日志/错误；`backend/app/models/task.py:7-19` 保存状态、数量、日志和错误；`backend/app/api/v1/tasks.py:49-169` 提供创建、停止和日志接口，以 `asyncio.create_task` 后台运行；`backend/app/crawler/scheduler.py:18-115` 用 APScheduler 读取启用规则并按五段 cron 执行。结构已实现，但停止标志存在进程内，重启后丢失；定时路径最后无条件写 `success`，可能掩盖部分失败。
3. **Java/Spring Boot 实现：** 使用 `crawler_rule`、`crawler_task`、`crawler_task_log` 持久表；用 Spring `TaskScheduler` 或 Quartz 触发，受限线程池执行；取消标志写数据库，Worker 在分页边界检查；状态机限定 `PENDING → RUNNING → SUCCESS/PARTIAL_FAILED/FAILED/CANCELLED`；日志逐条结构化存储，禁止把所有日志塞进一个长文本字段。

### 4.2 字段规范化、去重更新和查询导出

1. **作用：** 把采集结果变为可检索、可维护、可重复执行的数据。
2. **原实现：** `backend/app/crawler/pipeline.py:7-129` 规范字段、解析 K/万/多薪等薪资、拆分城市区县并用静态词表抽取技能；`backend/app/models/job.py:7-30` 对 `(source_site, source_id)` 建唯一约束；`backend/app/crawler/engine.py:112-143` 先查询再更新或插入；`backend/app/api/v1/jobs.py:16-137` 支持条件分页和 Excel 导出。属于**已实现的结构**，但并非数据库原子 upsert，高并发时仍要防竞态。
3. **Java 实现：** 将薪资解析、地点映射和技能词表拆成可单测的纯函数；MySQL 建唯一索引，并使用事务与冲突更新策略；原始字段和规范字段分开保存；导出走异步任务并限制行数、字段和权限。

### 4.3 真实网站采集边界

`backend/app/crawler/sites/boss.py` 与 `zhilian.py` 主要用 `httpx + BeautifulSoup + 可配置选择器` 解析列表。列表字段经常缺少经验、学历和 JD，且现代招聘网站对直接 HTTP 请求限制严格。依赖清单含 Playwright，但核心采集路径主要不是 Playwright。因此“多站点真实稳定采集”只能判为**部分实现且运行未验证**。

- 优点：五个项目中最接近 Spring Boot 所需的任务/数据库管理骨架。
- 不足：进程内取消、错误状态不严谨、站点选择器易失效、未发现自动测试。
- 许可：README 声称 MIT，但未发现独立 `LICENSE`，复用前需确认。

## 5. ZhaopinData

### 5.1 智联详情页采集与检查点保存

1. **在我们的系统中有什么作用？** 为统一职位模型补齐详情字段，并说明长任务如何避免因验证码、崩溃或中断丢失全部结果。
2. **原项目通过什么代码实现？** `zhaopin_crawler.py:34-126` 初始化 Selenium、等待手动登录并管理列表/详情标签页；`:133-175` 用多个选择器找职位链接；`:177-312` 提取标题、薪资、地点、公司、描述/要求、学历、招聘人数和发布时间；`:366-454` 先收集 URL 再逐个打开详情以避免 stale element；`:517-600` 每 8 页保存检查点并在结束或中断时保存。`:456-472` 用 UTF-8 BOM 输出 CSV。仓库中的样例 CSV 证明曾生成结果，但不等于当前网站仍可成功采集。
3. **Java/Spring Boot 实现：** 只采用字段清单和检查点思想。设计 CSV/Excel 导入器、行级校验、失败原因表和可恢复批次；若确需浏览器采集，应做成隔离的、经授权的 Connector，不在 Spring Boot 主服务里长期运行 Selenium。

### 5.2 评价

- **已实现：** 单来源浏览器脚本、详情提取、CSV 和中途保存。
- **缺失：** 统一清洗、去重、数据库更新、任务管理和推荐。
- 多处绝对 XPath 对页面改版敏感；README 要求安装 `requirements.txt`，但仓库未发现该文件。
- `标准职业数据库.csv` 未被采集脚本引用，不能据此声称已实现职业分类。
- 许可为 **GPL-3.0**。若主项目不准备按 GPL 发布，不能直接复制或改编其代码；仅可依据公开行为与字段需求自主实现。

## 6. JobCrawlerSystem

### 6.1 任务编排与采集进程

1. **在我们的系统中有什么作用？** 展示较完整的任务生命周期：请求创建任务、队列派发、独立 Worker 执行、结果与状态回写。
2. **原项目通过什么代码实现？** `Django/CrawlerOperationProject/crawler_task/models.py:4-75` 定义任务和结果；`Django/CrawlerOperationProject/crawler_task/admin.py:39-97` 从管理端发起任务并持久化结果；`Django/CrawlerOperationProject/crawler_task/tasks.py:10-66` 定义 Celery 发送与周期刷新；`Scrapy/JobCrawlerProject/celery_worker.py:19-89` 在子进程运行 Scrapy 并通过标准输出收集 JSON。这个概念链路存在，但 `Django/CrawlerOperationProject/crawler_task/views.py:125-174` 创建任务后直接调用发送器，而发送器会轮询等待结果，因而 API 并非真正端到端异步，属于**部分实现**。
3. **Java/Spring Boot 实现：** 本科毕设采用“数据库任务表 + 受限线程池/Quartz”即可。Controller 只创建任务并立即返回 ID；Worker 独立更新心跳、进度和终态；前端轮询或 SSE 展示状态。只有并发量和可靠性测试证明有必要时再引入消息队列。

### 6.2 BOSS JSON 字段映射与重试

1. **作用：** 了解列表接口的分页、城市编码和来源字段到统一职位字段的映射。
2. **原实现：** `Scrapy/JobCrawlerProject/JobCrawlerProject/spiders/bossSpider.py:27-96` 生成城市与分页请求；`:118-159` 把 BOSS JSON 映射为 `JobItem`；`:193-217` 递增延迟重试。详情请求被注释，`:219-227` 虽有详情解析函数却未接入；README 也明确说明因反爬关闭详情采集。因此列表映射已实现，JD 详情仅为**未接通设计**。`Scrapy/JobCrawlerProject/JobCrawlerProject/pipelines.py:18-80` 写 MySQL，但只插入，不做去重或更新。
3. **Java 实现：** 若数据来源已获授权，用专用 Provider 映射来源 DTO，并实施超时、限速、指数退避、最大重试和熔断；来源响应只进入原始表，再经统一清洗服务入库。不得依赖未公开接口作为演示主链路。

### 6.3 不建议采用的部分

- Django + Celery + Redis + Scrapy + SQLAlchemy + Agent 对本毕设过重，增加部署和答辩解释成本。
- `Agent/JobAgentProject/agent/agent_tools.py:82-177` 允许自然语言触发采集和 SQL Agent。LLM 生成并执行任意 SQL 存在越权、注入和数据泄漏风险；应改为固定服务接口和参数白名单。
- 配置源码中存在硬编码密钥/数据库凭据模式。报告不记录具体值；主项目必须使用环境变量或密钥管理，并在日志中脱敏。
- 未发现许可证文件，不能默认可复制代码。

## 7. RoleFit

### 7.1 简历 OCR 与结构化画像

1. **在我们的系统中有什么作用？** 把上传简历转成可编辑、可匹配的求职者基本信息、经历和技能，而不是把整份简历文本直接交给推荐模型。
2. **原项目通过什么代码实现？** `career-planner/backend/app.py:1224-1380` 的 `/api/ai/resume/parse` 先让 OCR 模型读图片，再将同一 OCR 文本并行/错峰送入基础信息、经历和技能三类 LLM 提取任务；OCR 失败时回退到直接视觉解析，最后合并、清理并对齐标签。`career-planner/backend/llm_client.py:117-222` 处理 OpenAI 兼容请求、重试、JSON 解析和异常；`tag_aligner.py:9-180` 先清理查询，从标签中心召回候选，再让 LLM 选择标准标签。源码链路**已实现**，但真实 OCR/LLM 准确率、费用与延迟本轮未验证。
3. **Java/Spring Boot 实现：** 建立 `ResumeFileService → OcrProvider → LlmStructuredExtractionService → ProfileNormalizationService → SkillDictionaryService`。要求模型按 JSON Schema 返回 `ResumeParseResult`，服务端用 Bean Validation 校验；保留原文证据、模型版本和解析状态；用户确认/修改后才生成正式 `CandidateProfile`。

### 7.2 标准化岗位画像

1. **作用：** 将自由文本 JD 转为稳定的基本要求、技能树、能力、工具、软素质和成长潜力，供评分使用。
2. **原实现：** `job-admin/backend/job_profile_schema.py:137-168` 定义标准画像字段；`:207-328` 规范 JD 分段和技术栈叶/分支并去重；`:530-596` 完成整体归一化。`job-admin/backend/portrait_builder/pipeline_core.py` 与 `job-admin/backend/portrait_builder/api_processing.py` 实现分阶段提取，`docs/backend_02_pipe_workflow.md:21-212` 描述上传、预检、抽取、产物与可选应用流程。结构和处理链路存在；文档里的高并发/RPM 数字是其项目配置，不应成为本项目默认值。
3. **Java 实现：** 定义版本化 `JobProfile` JSON DTO，并把可筛选字段拆到 `job_skill`、学历、经验等关系字段。企业发布时做基础结构化；AI 画像作为异步增强任务，失败不阻塞职位发布，管理员可审阅后生效。

### 7.3 匹配、排序、解释和技能差距

1. **作用：** 产出稳定排名，同时告诉用户“为什么推荐、哪些能力命中、还缺什么”。
2. **原实现：** `job-admin/backend/backend_app/matching_service.py:522-591` 计算余弦相似度、等级修正和低频技能加权；`:1135-1222` 汇总技术栈/能力/工具及软素质/成长维度，技术类约占 90%；`:1277-1367` 输出精确、模糊、缺失和等级不匹配分组及分数明细；`:1388-1605` 使用 Qdrant 语义召回并可回退到本地 NumPy；`:1980-2068` 先按身份 ID 去重，避免误合并同公司同标题的不同职位；`:2071-2265` 形成 Safety/Target/Reach 分层；`:2737-2770` 将确定性列表评分和较慢的 LLM insight 分开。阈值和权重集中在 `job-admin/backend/backend_app/match_config.py:5-79`。这是五个项目中最完整的智能匹配参考。
3. **Java 实现：** 第一版只用 MySQL 候选过滤、标准技能 ID、等级与经验匹配、可配置加权和理由模板。保存每个维度的分数与证据。数据量和离线评估证明关键词召回不足后，再增加外部 Embedding 服务与向量存储；向量只负责召回，不直接替代规则评分。LLM 解释异步生成且必须引用已计算证据。

### 7.4 风险与许可

- 简历和投递属于高敏感个人数据：需最小化上传、访问控制、删除机制、日志脱敏，并确认第三方模型的数据保留政策。
- 简历/JD 可能包含提示注入文本；系统提示中要明确其仅为数据，并采用结构化输出、字段白名单和长度限制。
- 模型 JSON 不稳定、限流、成本和向量模型版本漂移都需记录与降级策略。
- 部分前端/趋势功能含演示回退或 TODO，不能从界面推断后端均已完成。
- 仓库有真实 **MIT LICENSE**，但仍应仅迁移必要思想与少量可确认许可的代码；其 FastAPI、React、SQLite、Qdrant 和多模型配置不应整套引入。

## 8. 横向对比与最佳参考来源

| 能力 | 最佳参考 | 次要补充 | 不应重复研究/直接采用 |
|---|---|---|---|
| 来源适配接口 | zhipin-shield `collect/adapters/base.py` | job-crawler 站点类 | 不为每个来源复制一套入库逻辑 |

## 9. 面向 Vue 3 + Spring Boot + MySQL 的总体设计

### 9.1 建议模块

| 模块 | 主要职责 | 核心类/接口建议 |
|---|---|---|
| `job-domain` | 职位、公司、来源、状态、版本 | `Job`、`Company`、`JobSourceRecord` |
| `job-source` | 站内、文件、授权外部来源适配 | `JobSourceProvider`、`JobFetchRequest`、`ExternalJobRaw` |
| `job-ingestion` | 规范化、校验、去重、更新 | `JobNormalizer`、`JobValidator`、`JobDeduplicator`、`JobUpsertService` |
| `crawler-task` | 规则、任务、调度、取消、重试、日志 | `CrawlerRuleService`、`CrawlerTaskWorker`、`TaskScheduler` |
| `profile-ai` | 简历文件、OCR、结构化抽取、标准化、人工确认 | `OcrProvider`、`LlmStructuredExtractionService`、`ProfileReviewService` |
| `recommendation` | 候选过滤、维度评分、排序、理由、差距 | `CandidateRetriever`、`MatchScorer`、`RecommendationExplanationService` |
| `recruitment` | 企业发职、求职者投递、申请状态流转 | `JobPublishService`、`ApplicationService` |
| `admin` | 导入复核、任务监控、职位质量与来源管理 | 审核 API 与 Vue 管理页面 |

### 9.2 数据处理流程

```text
站内发布 / 文件导入 / 授权来源
        ↓ JobSourceProvider
ExternalJobRaw → 原始记录留档 → 规范化 → 校验 → 去重 → 事务性 upsert
                                                     ↓
                                              统一 job / job_skill
                                                     ↓
简历上传 → OCR → LLM 结构化 → 技能标准化 → 用户确认画像
                                                     ↓
               候选过滤 → 确定性分维度评分 → 排序 → 理由/技能差距
                                                     ↓
                                         Vue 推荐页与投递业务
```

### 9.3 建议核心表

- `job`：统一职位主体、发布方、状态、规范地点/薪资、首次与最后发现时间。
- `job_source_record`：来源 ID、来源 URL、原始 JSON、内容哈希、抓取批次和时间。
- `job_skill`、`skill_dictionary`：职位技能、标准技能、别名、等级和证据。
- `crawler_rule`、`crawler_task`、`crawler_task_log`：规则、生命周期、进度、结构化错误。
- `resume`、`candidate_profile`、`candidate_skill`：文件元数据、解析版本、用户确认后的画像。
- `recommendation_result`、`recommendation_dimension`：总分、维度分、证据、理由和模型/规则版本。
- `application`：投递人与职位、状态、时间线；与外部采集逻辑完全分离。

### 9.4 关键 API 建议

- 管理端：`POST /api/admin/imports`、`POST /api/admin/crawler-tasks`、`GET /api/admin/crawler-tasks/{id}`、`POST /{id}/cancel`。
- 企业端：`POST /api/company/jobs`、`PUT /api/company/jobs/{id}`、`GET /api/company/applications`、`PUT /api/company/applications/{id}/status`。
- 求职者端：`POST /api/resumes`、`POST /api/resumes/{id}/parse`、`PUT /api/candidate-profile`、`GET /api/recommendations`、`POST /api/jobs/{id}/applications`。
- AI 接口均异步返回任务 ID；列表推荐必须可在 AI 解释不可用时正常返回。

## 10. 开发优先级

### P0：形成可演示业务闭环

- 企业发布/维护站内职位，求职者浏览、投递，企业处理申请。
- 统一职位表、来源记录、文件导入、字段校验、来源 ID 去重与增量更新。
- 建立任务/日志最小骨架，但先以人工触发导入为主。
- 完成技能词典初版和可测试的薪资、城市、经验规范化。

### P1：完成“智能推荐”核心价值

- 简历上传、OCR/文本抽取、结构化画像和用户可编辑确认。
- 岗位技能画像、确定性加权评分、排序、推荐理由与技能差距。
- 保存分数证据和规则版本，准备少量人工标注样例做离线对比。

### P2：提高数据时效与可靠性

- 对经授权来源或公开数据文件做定时增量更新。
- 增加取消、重试、心跳、部分失败、过期/下架职位处理和质量监控。
- 评估 LLM 提取准确率、费用、延迟和隐私策略。

### P3：有证据再扩展

- 关键词召回不足时再接 Embedding/向量检索。
- 有足够行为数据后再做浏览/收藏/投递偏好调整或协同过滤。
- 暂缓分布式爬虫集群、无限制 SQL Agent、复杂多模型编排。

## 11. 许可证、安全与尚未验证事项

### 11.1 许可证边界

- RoleFit：仓库存在 MIT `LICENSE`。
- ZhaopinData：GPL-3.0，禁止在未接受 GPL 义务的情况下复制/改编代码到主项目。
- zhipin-shield、job-crawler：README 声称 MIT，但未发现独立许可证文件。
- JobCrawlerSystem：未发现许可证文件。
- 未明确授权的仓库默认只有阅读和思想参考，不应复制源码。正式采用任何片段前记录来源、提交、许可证和修改内容。

### 11.2 正式开发前必须验证

1. **数据合法性：** 每个外部来源的服务条款、robots/公开 API、学校演示范围、数据保存与展示授权。
2. **来源可用性：** 当前页面/API 字段、登录/验证码、频率限制和反爬；只能在隔离测试账号和限速条件下验证。
3. **统一模型：** 用真实样本确认薪资周期、多薪、地点、经验、学历、职位关闭状态和来源 ID 的映射规则。
4. **去重质量：** 构造同一职位跨来源、同公司同名不同地点、职位更新/重发样本，评估误合并与漏合并率。
5. **任务可靠性：** 进程重启、超时、取消、部分失败、重复执行和数据库唯一键竞态。
6. **AI 结构化质量：** 对脱敏简历/JD 建立人工真值集，测字段准确率、技能对齐率、JSON 失败率、延迟和单次成本。
7. **推荐有效性：** 让用户或导师对一小批“候选人—职位”对标注相关等级，比较基线规则、权重调整和可选向量召回。
8. **隐私与安全：** 文件类型/大小/恶意内容、提示注入、越权访问、第三方模型保留政策、删除与审计机制。
9. **依赖与漏洞：** 开发前锁定 Java/Node 版本，执行依赖许可证和漏洞扫描；本轮未安装或扫描第三方依赖。
